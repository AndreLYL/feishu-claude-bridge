# 飞书 Cloud Bridge —— 顶层愿景与架构设计

> 状态：愿景定稿（待用户评审）
> 日期：2026-06-23
> 性质：**顶层愿景文档**。它定义北极星、架构主决策、特色定位，并把工程拆成 3 个独立子项目。
> 每个子项目随后各自走独立的 设计(spec) → 计划(plan) → 实现 循环，不在本文展开实现细节。

---

## 1. 背景与定位

本项目当前形态：Python + `tmux send-keys`（输入）+ `JSONL 1 秒轮询`（输出），接管一个已在运行的 Claude Code 会话。

我们调研了同类标杆 **CC Connect（chenhg5/cc-connect）**，它的关键实现是：

- 用 **stream-json 子进程**（`claude --input-format stream-json`）驱动 Claude，结构化双向 IO，**不接管 tmux**、自己拉起进程；
- 中央 **Engine** 编排一切，**插件注册**（agent/platform 自注册）、**接口能力发现**（platform 通过实现可选接口来 opt-in 特性）；
- 横向覆盖 10+ IM 平台；
- **飞书 Card 2.0** 流式卡片、可折叠泳道、回调前缀路由（`nav:`/`act:`/`perm:`/`askq:`）；
- 双服务 Web 控制台（Management REST + Bridge WS）；
- 一整套稳定性手段（见 §7）。

**我们的差异化定位**：不追求横向铺平台，而是**把飞书一个平台做深**——把"聊天气泡流"升级成"**可导航的任务工作台**"，并把稳定性做到"像后台服务"。

> 一个被明确接受的取舍：转向 stream-json 后，桥接层自己托管 Claude 进程，**失去"坐在电脑前用同一个 TUI 实时围观/接手"**的体验；但 **MCP、工具链、Skills、订阅计费（不走 API key）全部保留**——它们来自 Claude Code 配置，与 IO 方式无关。卖点因此从"接管你手敲的会话"升级为"**托管一个保留全套 Claude Code 能力、且具备原生流式与高可用的会话**"。

---

## 2. 北极星（North Star）

> **"在飞书里托管一个高可用的 Claude Code 会话——它不是一串聊天气泡，而是一个可导航的任务工作台：每个任务是一张实时流式生长的精美工单，整体稳得像后台服务。"**

三个产品诉求对应三大支柱：

| 用户诉求 | 支柱 |
|---|---|
| 极高的稳定性 | **稳**：stream-json 核心 + 中央 Engine + 一整套可靠性机制 + 可视化"连接健康" |
| 更加美观的卡片 | **美**：任务工单卡（方向 B），Card 2.0 流式 + 折叠泳道 + 状态色 |
| 更丰富的交互 / 远端"页面" | **活**：控制台外壳（方向 A），`nav:` 卡片页面导航 + 按钮/表单/下拉真实回调 |

---

## 3. 架构主决策

1. **核心 IO：stream-json**（替换 tmux send-keys + JSONL 轮询）。桥接层拉起并托管 `claude` 进程，按行解析结构化事件（`system`/`assistant`/`result`/`control_request`/`user`）。
2. **平台范围：飞书单平台做深**。不引入 CC Connect 的多平台抽象层（YAGNI），但保留"渲染层 / 引擎层"的清晰边界，便于未来扩展。
3. **核心架构：中央 Engine + 可插拔 SessionDriver**。
   - `Engine`：单一编排者，持有会话状态、消息队列、去重、回合生命周期。
   - `SessionDriver`：会话驱动抽象。首发实现 `StreamJsonDriver`；保留接口，未来可加回 `TmuxDriver`（若需要）。
   - `FeishuRenderer` / `FeishuGateway`：飞书侧收发与卡片渲染，与 Engine 解耦。
4. **语言：沿用 Python**（现有代码与团队栈一致；CC Connect 的 Go 形态不强求移植，借鉴的是机制而非语言）。

## 4. 产品模型：分层组合 B + A + C

### 4.1 方向 B（核心）—— 任务工单卡

每个回合（turn）= 一张**会生长的精美工单卡**，原地流式演化，自上而下：

```
┌───────────────────────────────────────────┐
│ [状态色头部]  ▶ 正在处理 / ✓ 完成 / ✕ 出错   │
├───────────────────────────────────────────┤
│ 目标：<用户这轮请求的摘要>                    │
│ 计划：☑ 步骤1  ☐ 步骤2  ☐ 步骤3   (todo)     │
│ ▸ 推理过程 (3)        ← 可折叠泳道（默认收起） │
│ ▸ 工具调用 (Read×2, Edit, Bash)  ← 可折叠泳道 │
│ ─────────────────────────────────────────  │
│ <最终回复，流式打字机更新>                    │
│ ─────────────────────────────────────────  │
│ Opus 4.8 · 2.1k tokens · 12.4s   (暗色脚注)  │
└───────────────────────────────────────────┘
```

- 用 Card 2.0 `streaming_mode` + `element_id` 局部刷新做**真·打字机流式**，不重发整卡。
- 推理/工具分两条**可折叠泳道**，最终卡片保持简洁；想看细节再展开。
- 头部颜色随状态变（蓝=进行中 / 绿=完成 / 红=错误 / 橙=待授权）。

### 4.2 方向 A（外壳）—— 可导航控制台

一张常驻"主控台"卡片，用 `nav:` 回调在**原地切换"页面"**，让飞书像个 App：

- **首页**：当前会话名 · 状态 · 连接健康 · 快捷操作（新建 / 切换 / 中断 / 截图）
- **会话页**：会话列表（▶ 当前）、切换、批量删除（表单 checker 多选）
- **任务页**：当前/历史工单入口
- **设置页**：模型、权限模式、心跳开关等

### 4.3 方向 C（后期特色，不进地基）—— 飞书原生集成

路线图后期"加分项"：会话/任务列表同步**多维表格**、长产出落**飞书文档**、`@提醒`、定时心跳推送、卡片转发协作。**v1 不做**，仅在架构上不堵死。

## 5. 我们相对 CC Connect 的"特色签名"

1. **任务工单卡**：以"任务"而非"消息"为一等公民，目标/计划/工具流/产出聚合在一张生长卡里——直接回应"CC Connect 显示过于单一"。
2. **飞书页面化外壳**：`nav:` 驱动的可导航控制台，体验从"刷消息"变"用 App"——回应"远端前端页面怎么看"。
3. **可视化的稳定性**：把连接健康、队列深度、重连、最近错误做成一张"系统状态"卡，让"稳"看得见。
4. **飞书深度集成（后期）**：把 Claude 产出变成活的飞书原生物料（多维表格/文档），CC Connect 完全没碰。

---

## 6. 三大支柱落地要点

- **稳**：stream-json 核心；去重 + 启动水位线；有界队列 + 背压；会话状态原子落盘；优雅关闭三段式；事件空闲超时；单实例锁；daemon + 日志轮转；慢操作埋点；"连接健康"可视化。
- **美**：任务工单卡；Card 2.0 流式；折叠泳道；状态色头部；暗色脚注（模型·token·耗时）；统一 Card builder（杜绝裸 dict）。
- **活**：`nav:` 页面导航；按钮/表单/下拉真实回调（授权 allow/deny、askq 选择、会话切换、批量删除）；回调前缀路由（`nav:`/`act:`/`perm:`/`askq:`）。

> 注：现有 `feishu_client.py` 已注册 `CardActionHandler`，而 `formatter.py` 注释却称"WebSocket 不支持卡片回调"——这是一处**自相矛盾**。按钮交互很可能本就可用，子项目 3 须先验证打通，纠正该注释。

---

## 7. 借鉴 CC Connect 的稳定性机制（清单）

1. 消息去重 + **启动水位线**（丢弃进程启动前的旧消息，杜绝崩溃重放）。
2. **有界消息队列 + 背压**（每会话上限 N，满则回复"队列已满"，不静默丢弃、不无限阻塞）。
3. 会话状态 **原子落盘**（临时文件 + rename，崩溃不损坏，重启原样恢复）。
4. **优雅关闭三段式**（关 stdin → SIGTERM → SIGKILL）。
5. **重试 + 指数退避**（如 0/500/1500ms），异步未就绪时挂起到就绪事件。
6. **事件空闲超时**（无 agent 事件即判回合结束并解锁会话）。
7. **慢操作埋点**（发送>2s、首事件>15s 即告警）。
8. **per-session 互斥 + busy 标志**（`TryLock` 让心跳等快速跳过而非阻塞）。
9. **单实例锁**（flock，防多开打架）。
10. **daemon 管理**（systemd/launchd + 日志轮转 + 安装时捕获环境/代理）。

## 8. 工程拆分：3 个子项目（依赖链）

```
子项目 1：核心引擎 + stream-json 驱动 + 稳定性地基   ← 一切前提，服务"稳"
                          │
                          ▼
子项目 2：流式 Card 2.0 美观渲染系统（任务工单卡）    ← 服务"美"
                          │
                          ▼
子项目 3：丰富交互 + 飞书页面化控制台外壳            ← 服务"活"
```

### 子项目 1 —— 核心引擎 + stream-json + 稳定性地基
- 范围：`Engine` 编排器；`SessionDriver` 抽象 + `StreamJsonDriver`；§7 全部稳定性机制；连接健康模型；保留现有飞书收发但渲染先沿用旧 formatter（占位）。
- 产出验收：能稳定收发一个完整回合；崩溃重启不丢/不重放；队列背压可见；通过集成测试。

### 子项目 2 —— 流式 Card 2.0 渲染系统
- 范围：统一 Card builder；任务工单卡；Card 2.0 `streaming_mode` 打字机；折叠泳道（推理/工具）；状态色头部；暗色脚注。依赖子项目 1 的结构化事件流。
- 产出验收：一个回合在飞书呈现为单张流式生长的工单卡，推理/工具可折叠。

### 子项目 3 —— 丰富交互 + 页面化控制台
- 范围：先验证并打通卡片回调；回调前缀路由；授权 allow/deny、askq 选择按钮/下拉；`nav:` 控制台外壳（首页/会话/任务/设置）；批量删除表单。依赖 1+2。
- 产出验收：可在飞书内用按钮完成授权/选择/会话切换/翻页，无需输入命令。

## 9. 非目标 / YAGNI（v1 不做）

- 不做多平台（Telegram/Slack/…）；不做 CC Connect 的平台抽象层。
- 不做独立浏览器 Web 控制台（公网 IP 问题）；"页面化"用飞书卡片实现。
- 不做"预览 Claude 所开发的 dev server 网页"（截图/隧道）——已确认不是本期诉求。
- 方向 C（多维表格/文档集成）列入后期，不进 v1 地基。
- 不强制移植到 Go；沿用 Python。

---

## 10. 风险与开放问题

- **R1**：stream-json headless 模式下，权限提示（`control_request`）与 Claude Code 交互式权限的语义差异，需在子项目 1 验证。
- **R2**：飞书 Card 2.0 `streaming_mode` 的局部刷新 API 在 lark-oapi Python SDK 的可用性/配额，需在子项目 2 先做技术验证（spike）。
- **R3**：WebSocket 长连模式下卡片回调的可达性（与现有矛盾注释相关），子项目 3 先验证。
- **R4**：失去本地 TUI 围观能力对你的实际工作流影响——若后续后悔，可通过保留的 `SessionDriver` 接口加回 `TmuxDriver`。
